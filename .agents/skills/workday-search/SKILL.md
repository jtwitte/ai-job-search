# Workday Search Skill

Search job listings on **any Workday-powered career site** — a multi-tenant enterprise ATS,
so this one skill covers every company that uses it, not just one. Pass the site via
`--site`, the same way `teamtailor-search` takes `--site`. No authentication, no API key,
and **zero runtime dependencies** — it runs with just `bun`.

> Generated by `/add-portal` (2026-08-11), starting from Husqvarna Group's Workday site
> (`husqvarnagroup.wd3.myworkdayjobs.com/External_Career_Site`). Built generic from the
> start, matching the `teamtailor-search` precedent, since Workday's `/wday/cxs/<tenant>/
> <siteId>/` API shape is identical across every tenant. Per repo policy this lives in the
> fork rather than being merged upstream.

## ⚠️ Per-site AI-access check

Like `teamtailor-search`, this CLI checks `robots.txt`'s `Content-Signal: ai-input` live for
whichever `--site` you pass, before every request, and refuses to proceed
(`AI_INPUT_DISALLOWED`) if that site has opted out. Not observed on Husqvarna's own
robots.txt (no `Content-Signal` line at all there), but checked defensively per-site since
it's a Workday-tenant-configurable setting on the same underlying signal used elsewhere.

## When to use this skill

- Search a specific company's open roles, when you know (or suspect) their career page runs on Workday
- Get the full description of a specific job listing (deadline, employer, employment type)

If you don't know whether a company uses Workday: their career site is typically at
`<tenant>.wdN.myworkdayjobs.com/<siteId>` (visible in the URL bar when browsing their
careers page) — `search` fails cleanly with `NOT_FOUND` if the CXS API doesn't respond there.

## Commands

### Search job listings

```bash
bun run .agents/skills/workday-search/cli/src/cli.ts search --site <host/siteId> [flags]
```

Key flags:
- `--site <host/siteId>` / `-s <text>` — **required.** e.g. `"husqvarnagroup.wd3.myworkdayjobs.com/External_Career_Site"`. A locale segment (`/en-US/...`) is fine — only the last path segment is used as the siteId.
- `--query <text>` / `-q <text>` — keyword filter. Server-side (unlike `teamtailor-search`'s client-side filter) — matched against title, location, and requisition id.
- `--location <text>` / `-l <text>` — free-text location filter, combined into the same search string as `--query` (Workday's real faceted location filter needs opaque per-tenant IDs this CLI doesn't resolve — see `url-reference.md`).
- `--page <n>` — page number (1-indexed).
- `--limit <n>` / `-n <n>` — results per page / cap. Default 20.
- `--format json|table|plain` — default `json`.

Pagination is real server-side pagination here (confirmed live), unlike the RSS-based skills
in this repo — fine to page through large tenants (Husqvarna has 158+ open roles at time of
testing) without fetching everything at once.

### Fetch full job detail

```bash
bun run .agents/skills/workday-search/cli/src/cli.ts detail <reqId|url> [--site <host/siteId>] [--format json|plain]
```

`reqId` is the requisition id from `search` results (e.g. `R-17833`) — pass `--site`
alongside it. A full job URL (as returned by `search`) needs no `--site`, since host and
siteId are both derivable from it.

## Usage examples

```bash
# All open roles at Husqvarna Group
bun run .agents/skills/workday-search/cli/src/cli.ts search -s husqvarnagroup.wd3.myworkdayjobs.com/External_Career_Site --format table

# Robotics roles specifically (Husqvarna's Residential Robotics R&D is based in Huskvarna,
# Jan-Torben's home town)
bun run .agents/skills/workday-search/cli/src/cli.ts search -s husqvarnagroup.wd3.myworkdayjobs.com/External_Career_Site -q "Robotics" --format table

# Full details for a specific job (requisition id + --site)
bun run .agents/skills/workday-search/cli/src/cli.ts detail R-17833 -s husqvarnagroup.wd3.myworkdayjobs.com/External_Career_Site --format plain

# Full details via URL (no --site needed)
bun run .agents/skills/workday-search/cli/src/cli.ts detail "https://husqvarnagroup.wd3.myworkdayjobs.com/External_Career_Site/job/Huskvarna/...-R-17833" --format plain
```

## Output formats

| Format | Best for |
|--------|----------|
| `json` | Default — programmatic use, passing IDs to `detail` |
| `table` | Quick human-readable scanning |
| `plain` | Reading a single job's full detail (`detail` command) |

All errors are written to **stderr** as `{ "error": "...", "code": "..." }` and the process exits with code `1`.

## Notes

- Data is from each tenant's public Workday CXS JSON API (`/wday/cxs/<tenant>/<siteId>/`) — no credentials required, and no company-specific parsing code: the same logic works for any Workday customer.
- **`search`'s `date` field is relative text** ("Posted Today", "Posted Yesterday", "Posted 4 Days Ago"), not an ISO date — Workday's list API doesn't expose one. `detail`'s `datePosted`/`deadline` *are* real ISO dates.
- **`search` results have no `company` field** (`null`) — the employer name only appears in `detail`'s output, from `hiringOrganization.name`.
- Descriptions come back as clean plain text (HTML stripped, entities decoded) in `detail`'s output.
- Job IDs are requisition numbers like `R-17833` — a bare id needs `--site` (detail re-searches to resolve the full slugged path, since Workday 404s on a bare id with no slug).
- See `url-reference.md` for the full endpoint reference, the `Content-Signal` access-check design, and a note on a URL-construction bug caught and fixed during setup (`search` results' `url` field needed the siteId segment, which the API's own `externalPath` field omits).
