# Teamtailor Search Skill

Search job listings on **any Teamtailor-powered career site** — a multi-tenant ATS, so this
one skill covers every company that uses it, not just one. Pass the site's domain via
`--site`, the same way `linkedin-search` takes `--location`. No authentication, no API key,
and **zero runtime dependencies** — it runs with just `bun`.

> Generated by `/add-portal` (2026-08-11), starting from `career.ivl.se`. Built generic
> rather than IVL-specific once Teamtailor's multi-tenant RSS/JSON-LD pattern was confirmed
> against a second tenant (`career.ri.se`, RISE) during setup. Per repo policy this lives in
> the fork rather than being merged upstream.

## ⚠️ Per-site AI-access check — some Teamtailor sites will refuse

Every Teamtailor tenant can opt out of AI-agent access via `robots.txt`'s
`Content-Signal: ai-input=no` — confirmed live that this varies per company (**career.ivl.se
says yes; career.ri.se (RISE) says no**, on an otherwise identical robots.txt template).
This CLI checks the signal live for whichever `--site` you pass and **refuses to proceed**
(`AI_INPUT_DISALLOWED`) if that site has opted out. This isn't a flag you can override — if a
site says no, check it manually in a browser instead. See `url-reference.md` for detail.

## When to use this skill

- Search a specific company's open roles, when you know (or suspect) their career page runs on Teamtailor
- Get the full description of a specific job listing (deadline, employer, employment type)

If you don't know whether a company uses Teamtailor: their career subdomain is often
`career.<company>.<tld>` or similar, and `search` will fail cleanly with `NOT_FOUND` if
`/jobs.rss` doesn't exist there.

## Commands

### Search job listings

```bash
bun run .agents/skills/teamtailor-search/cli/src/cli.ts search --site <domain> [flags]
```

Key flags:
- `--site <domain>` / `-s <domain>` — **required.** e.g. `"career.ivl.se"`, `"career.ri.se"`.
- `--query <text>` / `-q <text>` — keyword filter (title/department/location/description). Client-side — the feed has no server-side search.
- `--location <text>` / `-l <text>` — filter by city/location text. Also client-side.
- `--jobage <days>` — posted within N days (filtered against the feed's `pubDate`).
- `--locale <code>` — feed locale, e.g. `"en-GB"`. Omit for the site's default-locale feed.
- `--page <n>` — page number (1-indexed).
- `--limit <n>` / `-n <n>` — results per page / cap. Default 20.
- `--format json|table|plain` — default `json`.

Every open role for a site comes back in one RSS fetch (no pagination on Teamtailor's end),
so this is fine for the small per-employer counts typical of a single company — don't expect
it to behave like a cross-company aggregator.

### Fetch full job detail

```bash
bun run .agents/skills/teamtailor-search/cli/src/cli.ts detail <id|url> [--site <domain>] [--format json|plain]
```

`id` is the numeric job ID from `search` results (e.g. `7988741`) — pass `--site` alongside
it. A full job URL (as returned by `search`) needs no `--site`, since the domain is already
in it. Returns the full description, employer, employment type, posted date, and deadline.

## Usage examples

```bash
# All open roles at IVL (Swedish Environmental Research Institute)
bun run .agents/skills/teamtailor-search/cli/src/cli.ts search -s career.ivl.se --format table

# Keyword filter
bun run .agents/skills/teamtailor-search/cli/src/cli.ts search -s career.ivl.se -q "avloppsvatten" --format table

# English-locale feed
bun run .agents/skills/teamtailor-search/cli/src/cli.ts search -s career.ivl.se --locale en-GB --format table

# Full details for a specific job (bare id + --site)
bun run .agents/skills/teamtailor-search/cli/src/cli.ts detail 7988741 -s career.ivl.se --format plain

# Full details via URL (no --site needed)
bun run .agents/skills/teamtailor-search/cli/src/cli.ts detail https://career.ivl.se/jobs/7988741-institutsdoktorand --format plain
```

## Output formats

| Format | Best for |
|--------|----------|
| `json` | Default — programmatic use, passing IDs to `detail` |
| `table` | Quick human-readable scanning |
| `plain` | Reading a single job's full detail (`detail` command) |

All errors are written to **stderr** as `{ "error": "...", "code": "..." }` and the process exits with code `1`.

## Notes

- Data is from each tenant's public `/jobs.rss` feed (search) and schema.org `JobPosting` JSON-LD (detail) — no credentials required, and no company-specific parsing code: the same logic works for any Teamtailor customer.
- Descriptions come back as clean plain text (HTML stripped, entities decoded) in both `search`'s internal matching and `detail`'s output.
- Job IDs are numeric (e.g. `7988741`) — a bare `/jobs/<id>` (no slug, no locale) resolves fine, confirmed live.
- **`--location`/`-l` and `--query`/`-q` are both client-side filters**, not server parameters — the RSS feed has no search API. Fine for a single employer's small job count; don't rely on this for large-scale cross-company search.
- See `url-reference.md` for the full endpoint reference, the `Content-Signal` access-check design, and quirks found during setup.
